### Coupling mechanism legend

- **codegen**: dependent is machine-generated from the source; stays in
  sync if the generation step runs.
- **shared-import**: dependent reads the source at build or run time; the
  toolchain or the tool enforces the contract.
- **manual-mirror**: dependent restates the source by hand; no automated
  enforcement.
- **contract-test**: a dedicated test asserts agreement.
- **build-step**: a build step fails if the artifacts disagree.
- **runtime-validation**: caught at run time, not at build or test time.
- **none**: no known enforcement.

### Propagation mode legend

- **build-error** / **test-failure**: loud, in `make check` or CI.
- **runtime-error**: loud only when the path runs (a tarball user, a
  release).
- **silent**: the dependent is wrong and nothing says so.

### Finding 1: The profile list is typed into three gates

**Source**: `adpat/c/cadapt.c` — the profiles `--fast`, `--mid`, `--max`
(the usage and `print_usage`); `--mid` arrived on 2026-09-16.
**Dependent**: `.github/workflows/ci.yml:94` — `for flags in "" "--fast"
"--mid" "--max --allocation context --contexts lean" "--max --allocation
context -6"`; `tools/check_memory.py:44` — `DEFAULT_COMMANDS = ["",
"--fast", "--mid", "--max", "--max -6"]`; `Makefile:90` (the comment
naming the same five).
**Mechanism**: manual-mirror
**Guard**: ⚠ NONE

**How drift manifests**: a fourth profile lands with its own per-byte and
per-bit paths. `make check` and the CLI suite pass. The identical-bytes job
still compares five flag sets, none of them the new profile, so a
gcc/clang or AVX2/baseline divergence in it ships unseen — the exact
failure RUN-5 exists to catch. The memory gate never measures its peak
against its declaration.

**Recommended fix**: make the profile list a product of the binary.
`cadapt --help` already prints `[--fast | --mid | --max]`; give the
binary `cadapt --list-profiles` (or parse the usage's bracket group, as
`tools/test_docs.py` already tokenizes it) and have `check_memory.py` and
the identical-bytes step build their command lists from it — the flags per
profile stay in one table in `tools/`. Add to `tools/test_docs.py` a test
that every profile flag of `--help` appears in that table. Run in `make
check`.

### Finding 5: The committed build manifest is stale by construction

**Source**: the tree at HEAD (`adpat/c/*` and the toolchain).
**Dependent**: `build-manifest.json` at the repository root — records
commit `150a4c6`, last regenerated in `0078b3e` (2026-09-16), 30-odd

`cadapt-<version>-src.tar.gz`; `docs/release-pipeline.md:56` says `python3

**Mechanism**: manual-mirror (`make manifest` by hand)
**Guard**: ⚠ NONE (`make reproduce` on this tree: "adpat/c/Makefile differs
from the manifest's — not the manifest's sources: nothing to reproduce")

**How drift manifests**: a reader of the source tarball, or of the tree,
runs `make reproduce` as the pipeline document says and gets a refusal;
the record names a build nobody can match. The manifest that matters —
the one `tools/release.sh` writes beside each artifact — is correct, so

by a test because it records the commit hash of the tree it describes.

**Recommended fix**: stop tracking `build-manifest.json` at the root
(`git rm`, add to `.gitignore`), drop it from the `git archive` list in
`tools/release.sh` and from the SBOM/manifest section of
`docs/release-pipeline.md`; state that the build manifest is a release
artifact only (`dist/<version>/build-manifest.json`). If a committed record
is wanted, commit it under `docs/release-notes/<version>-build-manifest.json`
*after* the tag, as a record of that build, never as a description of HEAD.

### Heuristic limitations

This analysis is based on static file-pattern matching (`grep`, `find`,
reading the Makefiles and workflows) and on the tests' names and bodies.
It cannot detect couplings mediated by run-time reflection, couplings that
cross into other repositories or hosts (the LTCB page, the reference
runner), semantic equivalence of two definitions that look different, or
the completeness of a test suite — a "test-failure" propagation mode
assumes the named test covers the path. Line numbers are those of
`dfc66c5` and move with the files.
